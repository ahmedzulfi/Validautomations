Every component, measured. Frame by frame.

Each glowkit component renders headlessly for 120 frames of simulated time with the pointer moving across it. We time the UI pass and tessellation, count vertices and allocations, and check whether it keeps asking for frames when nothing is happening.

Methodology

How these numbers are made

Run it yourself: the harness lives in apps/bench.

Harness

  • One fresh egui::Context per component, gallery fonts and the light theme installed, warmed with one empty frame so "cold" measures the component and not egui's font atlas.
  • Fixed 1100×720 viewport at 1 pixel per point. The component sits in the same padded preview card the gallery uses.
  • 120 frames with time advancing 1/60 s each; the pointer moves along a Lissajous path so hover effects and cursor-driven components do real work.
  • Per frame: wall time of ctx.run_ui and ctx.tessellate, primitive/vertex/index counts, allocation count and peak extra heap bytes from a counting global allocator.
  • Median, p95 and max exclude the first ("cold") frame. Then the pointer leaves and 30 idle frames run; the requested repaint delay over the last 10 decides the idle-repaint class.
  • Panicking components are caught with catch_unwind, and components that stop making progress for 90 s (e.g. a deadlock) are abandoned by a watchdog; both are listed as errors.
cargo run --release -p glowkit-bench -- \
  --frames 120 --json website/benchmarks.json

Machine & build

Caveats

  • Headless CPU time only. GPU rasterization, texture upload and presentation are not included; a real frame also pays for those, usually a small fixed cost for 2D meshes of this size.
  • Single-threaded, sequential runs on a shared machine; expect a few percent of noise, more on sub-0.05 ms numbers.
  • App memory is the peak RSS of a gallery-equivalent workload (every category page rendered as a tile grid in one long-lived context), measured in a child process, not of the windowed gallery with a GPU surface.

External context (not measured here)

For orientation only, typical published ballparks for an Electron "hello world": roughly 80–150 MB installer/binary footprint (it bundles Chromium) and 60–100 MB+ resident memory at idle. These figures are not produced by this harness and vary widely by app and platform; compare against your own builds.
